# 浏览器测试案例

每个 case 一个文件夹，案例说明和 Playwright 测试放在一起。这里保存探索后确认的用户场景；探索与生成测试的执行方式见 [通用提示词](../prompts/staging-explore-to-playwright.md)。

已建立首批公开页面案例、Playwright Test 配置和 `e2e:functional` 命令。以下目录展示案例约定。

## 设计原则：好维护、可读性高

所有新增与调整都以好维护、可读性高为首要设计原则，具体要求如下：

- **案例集中**：一个 case 一个文件夹，说明、测试和专用数据就近维护，避免为理解一个案例跨多个目录查找。
- **命名明确**：目录、测试和步骤名称直接表达用户行为及预期结果，使读者仅看名称就能理解测试目的。
- **流程直观**：代码按准备、操作、断言展开；阅读 spec 就能看清主要流程和失败条件，不把关键业务断言隐藏在多层辅助函数中。
- **结构简单**：只为当前明确的需求增加文件和层级，不预先搭建通用框架；抽取公共逻辑必须让调用处更容易理解和修改。
- **改动集中**：单个案例的业务变更应主要修改其自身文件夹；共享配置和工具职责明确，避免案例之间互相依赖。
- **说明一致**：修改行为时同步更新案例说明、定位契约和测试代码，让文档能够准确解释实际断言。

评审时检查：新维护者能否从案例文件夹快速理解测什么、如何准备、怎样操作、为何失败，以及需求变化时应该修改哪里。若一种抽象增加了理解成本，优先采用直接、清晰的实现。

## 目录与命名

```text
e2e/
├── prompts/
│   └── staging-explore-to-playwright.md
├── cases/
│   ├── README.md
│   ├── playwright.config.js
│   ├── glossary-001-search/
│   │   ├── README.md
│   │   └── test.spec.js
│   ├── glossary-002-detail-and-back/
│   │   ├── README.md
│   │   └── test.spec.js
│   └── _shared/                    # 有实际复用需求时再添加
└── reports/
    └── <运行时间>/
        ├── report.md
        └── glossary-001-search/    # 本次运行的截图等证据
```

- 文件夹使用 `<功能>-<三位编号>-<场景>`，小写英文与连字符，例如 `glossary-001-search`。
- 案例编号对应 `GLOSSARY-001`，出现在说明、测试名称和运行报告中；新增编号不挤占旧编号，删除的编号不复用。
- 一个 case 描述一个用户场景及其预期，可以包含多个连续步骤。搜索成功和搜索无结果属于两个 case；同一流程的桌面与手机覆盖使用 Playwright projects，不复制文件夹。
- 每个真实案例至少有 `README.md` 和 `test.spec.js`，阅读一个文件夹即可了解目的、操作与断言。

## 案例说明模板

每个 case 的 `README.md` 使用以下结构。说明保存稳定的测试契约，实际执行结果放进运行报告。

```markdown
# GLOSSARY-001：搜索术语

## 目的

说明要验证的用户行为。

## 前置条件

- 优先级：P1
- 入口：/glossary
- 视口：桌面、手机
- 语言：简体中文
- 账号与数据：公开页面；列明所需测试数据

## 步骤与预期

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 | 描述操作 | 描述可验证的业务结果 |

## 定位契约

| 业务目标 | data-testid | 状态 |
| --- | --- | --- |
| 待验证控件 | 探索后填写 | 已确认／缺失／重复 |

## 关联问题

记录问题编号和必要背景；没有则写“无”。
```

## 测试代码约定

- `test.spec.js` 中按准备、操作、断言顺序编写，使用 `test.step()` 对应说明中的步骤。步骤不能拆成依赖前序状态的多个 `test()`。
- 所有 DOM 定位使用 `getByTestId()`；唯一目标先断言 `toHaveCount(1)`。缺失或匹配不唯一必须失败，不能改用其他定位方式、跳过测试或标记为预期失败。
- 简单数据留在 spec。只有确有需要时才在当前 case 添加 `data.js`、`helpers.js` 或 `fixtures/`。
- 跨案例的公共逻辑放在 `_shared/`，只有实际重复出现后才提取；case 之间不互相导入。
- 视口和通用超时在统一配置中维护，不为每个 case 单独创建 package.json 或配置文件。
- 功能变化时，在同一次改动中更新该 case 的说明与代码。失败时先确认原因，不能为了通过而直接修改预期。

## 运行与证据

生成测试时，在 `cases/playwright.config.js` 中使用 `testDir: '.'` 和 `testMatch: '**/test.spec.js'`，并在 `e2e/package.json` 新增 `e2e:functional` 命令：

```text
playwright test --config cases/playwright.config.js
```

这样不会被现有 `e2e/run-all.js` 当作普通 Node 脚本执行。配置和命令落地后，可从 `e2e/` 运行全部案例或选择单个案例：

```sh
pnpm run e2e:functional
pnpm run e2e:functional glossary-001-search/test.spec.js
```

目标地址从 `E2E_BASE_URL` 读取。报告、截图与 runner 产物统一输出到 `e2e/reports/`，每次运行独立目录，通过案例编号关联结果。CI 从此目录上传允许公开的报告；遵循仓库已有约定，不上传登录状态或 trace。

这些产物不提交 Git。现有 `visual/` 的已审查基准截图继续按其自身规范管理。
