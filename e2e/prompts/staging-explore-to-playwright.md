# Staging 探索与 Playwright 回归测试提示词

复制下方提示词交给执行任务的 agent。填写目标地址或提前设置 `E2E_BASE_URL`；其余参数可按默认值执行。

---

请使用 agent-browser 对 staging 做探索式测试，再将发现的关键流程固化为可在 CI 中运行的 Playwright Test 用例。请完成实际探索、问题记录、代码编写和验证。

## 输入与范围

- 目标地址：优先读取 `E2E_BASE_URL`，否则使用我提供的 `[staging HTTPS 根地址]`。缺失时向我询问，不猜测域名，不使用生产环境兜底。
- 重点功能：`[可选；默认覆盖公开页面的主要功能]`。
- 账号：`[可选；默认仅访问公开页面]`。需要登录时使用提供的测试账号或本地登录状态。
- 桌面视口：1440×900；手机视口：390×844。
- 首批固化 5～10 个关键案例；发现更多问题时全部记录，不受案例数量限制。
- 允许浏览、搜索、切换语言、操作菜单和填写测试内容。提交数据、发送消息、支付、删除等操作仅在明确授权范围内执行。

先阅读仓库说明、AGENTS.md、现有测试和 CI 配置，复用项目已有约定。需要了解代码且仓库存在 `.codegraph/` 时，先使用 CodeGraph。

## 设计规范：好维护、可读性高

目录组织、案例说明和测试代码都必须以好维护、可读性高为首要设计原则，并遵守 `e2e/cases/README.md` 的设计规范。

- 一个 case 一个文件夹，说明、代码和专用数据放在一起。
- 使用直接表达业务意图的名称，按准备、操作、断言组织代码，让主要步骤和失败条件一眼可见。
- 保持文件与目录层级简单；有实际复用需求时才提取公共逻辑，避免多层封装隐藏业务断言。
- 单个案例的修改尽量集中在自身目录，共享逻辑职责明确，案例之间独立。
- 文档、定位契约和断言同步维护；交付前从新维护者的角度检查，确保容易理解测试目的、运行条件、失败原因和修改位置。

## 定位规则：强制使用 data-testid

1. Playwright 中所有 DOM 元素定位统一使用 `getByTestId()`，包括点击、填写、等待和内容断言。使用默认 `data-testid` 属性，不把其他属性配置成 test ID。
2. 禁止用 `getByRole`、`getByText`、`getByLabel`、CSS/XPath、坐标点击或 JavaScript 触发事件兜底。禁止用 `.first()`、`.nth()` 掩盖本应唯一的目标发生重复的问题。
3. agent-browser 探索时，先检查当前 CLI 帮助，使用其按 test ID 定位的命令，例如 `find testid <id> click`。snapshot、截图和只读 DOM 检查可用于发现控件及其属性，但不能用 snapshot 的 `@ref`、文本或坐标代替 test ID 执行交互。
4. 需要操作或断言的业务目标缺少 `data-testid` 时，立即将该步骤记为失败，报告“缺少测试定位契约”，记录页面、目标控件、截图和建议 ID。该流程的后续依赖步骤记为阻塞，继续执行其他独立案例。
5. 缺少 ID 时不得临时向 DOM 注入属性，不得虚构已有 ID，不得绕过失败步骤后声称原流程通过。可以直接打开目标路由做独立页面测试，但它不能替代导航点击测试。
6. 需要唯一定位的目标先断言匹配数量为 1。列表条目可以采用稳定的业务 ID，或者先通过唯一容器的 `getByTestId()` 缩小范围，再通过子元素的 `getByTestId()` 定位。禁止依赖易变的显示顺序。
7. 该要求针对测试涉及的交互目标和业务断言目标，无需给所有装饰性 DOM 节点添加 ID。
8. URL、响应状态和网络错误等非 DOM 检查可直接使用对应 API。文本可以作为 test ID 定位之后的断言值。

## 第一阶段：实际探索并记录问题

1. 使用独立 agent-browser 会话打开目标站点，记录执行时间、视口、语言，以及能取得的部署版本。
2. 从首页开始检查主导航、页脚和站内链接，建立页面与功能清单。覆盖所有发现的主要页面类型；大量相同模板的内容页按不同内容状态抽样，记录样本和未覆盖范围。
3. 先截取页面和交互状态，再结合 snapshot 与只读属性检查确认可用的 test ID。对关键控件检查缺失、重复和不稳定 ID。
4. 实际验证主要用户流程，并覆盖适用的输入边界、空结果、无效参数、刷新、前进后退和语言切换。桌面和手机都执行关键流程。
5. 同时检查内容是否正确、操作后的反馈、控制台异常和失败请求。区分应用缺陷、第三方请求问题与访问环境阻塞，保留证据，避免把每一条控制台日志都判为产品缺陷。
6. 发现问题后尝试复现，保留首次失败与复现结果。记录问题编号、严重程度、URL、视口、前置条件、步骤、预期、实际结果和截图路径。
7. 不把 HTTP 200、页面打开成功或元素存在单独作为业务流程通过的依据。

## 第二阶段：整理可维护的案例

每个 case 使用独立文件夹，将案例说明与测试代码放在一起。先阅读 `e2e/cases/README.md`，按其中的目录与命名约定维护。每个案例说明包含：

- 稳定编号，例如 `GLOSSARY-001`。
- 测试目的、优先级、适用视口和语言。
- 前置条件、确定的测试数据。
- 操作步骤与逐步预期结果。
- 使用的 test ID 及其是否已存在。
- 关联的问题编号。

每次运行的实际结果、通过／失败／阻塞／未执行状态及截图统一放进运行报告，按案例编号关联，不反复改写案例说明中的预期。

预期结果应来自明确的产品需求、项目契约或可验证的业务规则。无法确定预期时说明缺少哪项信息，不把当前页面行为直接当成正确答案。

优先固化重要、预期明确的流程，复用现有覆盖，避免重复实现同一检查。

## 第三阶段：生成 Playwright Test 代码

使用 `@playwright/test`，每个 case 文件夹包含 `README.md` 和 `test.spec.js`，测试名称包含案例编号。一个 case 对应一个有明确预期的用户场景；步骤用 `test.step()` 表达。桌面、手机及语言变体复用同一案例，具有独立预期的正常、空结果或错误场景拆成不同 case。

代码要求：

- `baseURL` 从 `E2E_BASE_URL` 读取，校验为 HTTPS 根地址；缺失或无效时立即失败。
- 每个测试独立运行，显式准备语言、登录态和必要数据，不依赖前一个测试留下的状态。
- 所有 DOM 操作与断言遵守 `getByTestId()` 规则。
- 对单一操作目标先使用 `toHaveCount(1)`，再检查可见性、可用性和操作后的业务结果。
- 使用自动等待及可重试的 `expect` 断言，不用固定 sleep，也不把 networkidle 当成通用的页面就绪条件。
- 对搜索、跳转、提交等操作断言对应的实际结果，不能只验证按钮可点击。
- 给 action、navigation 和 test 配置合理的超时。
- 不使用 `test.skip`、`test.fixme`、预期失败标记、吞异常或删除断言掩盖已发现的问题。
- 因缺少 test ID 无法实现的核心步骤也必须保留为失败：若已有明确的 ID 契约，断言该 ID 存在；否则通过带问题编号和目标描述的明确失败暴露缺口。建议 ID 单独标记为待落实，不假装已经存在。
- 如果当前仓库包含业务源码且修改属于本次授权范围，可以补齐缺失 ID；否则报告源码仓库的待办。只有变更部署到 staging 并复测通过，才能关闭部署环境中的问题。
- 不因重试后偶尔通过就忽略不稳定案例；报告首次失败和重试结果。

目录按案例组织，不另设与案例说明分离的 `specs/` 目录。下面为目标结构示例，真实案例必须在探索后生成，不创建空测试占位：

```text
e2e/
  prompts/
    staging-explore-to-playwright.md
  cases/
    README.md
    playwright.config.js
    glossary-001-search/
      README.md
      test.spec.js
    glossary-002-detail-and-back/
      README.md
      test.spec.js
    _shared/                       # 确有跨案例复用需求时才创建
  reports/
    <运行时间>/
      report.md
      glossary-001-search/         # 该案例本次运行的证据
```

本仓库 `e2e/run-all.js` 会自动执行 `e2e/` 根目录下未排除的 `.js` 文件。新配置位于 `e2e/cases/playwright.config.js`，设置 `testDir: '.'`、`testMatch: '**/test.spec.js'`，通过独立命令 `e2e:functional` 调用 `playwright test --config cases/playwright.config.js`。新配置和 spec 不放在 `e2e/` 根目录。

优先让测试按“准备、操作、断言”的顺序直接可读。案例独有的数据或辅助函数留在该案例内；简单数据直接写在 spec，复杂数据才新建 `data.js` 或 `fixtures/`。只有多个案例确实需要相同逻辑时才提取到 `_shared/`，案例之间不得互相导入或依赖执行顺序。不要为单个测试搭建通用框架。

提示词、案例、测试源码和锁文件纳入 Git。运行报告、截图、登录状态和本地环境文件加入忽略规则。现有 `visual/` 中经过审查的视觉基准继续按既有方式管理。

## 第四阶段：接入并验证 CI

1. 检查现有 package manager、Node 版本、Playwright 版本和工作流，按项目约定安装并锁定依赖，避免不必要的升级。
2. 提供本地运行命令，通过环境变量传入目标地址。
3. 在 staging 部署就绪后执行功能测试。复用现有等待部署的机制；如果现有机制支持校验提交版本，沿用该能力。
4. CI 从 Secrets 读取目标地址和凭据，不把它们硬编码进仓库。
5. 配置 HTML 和机器可读报告，失败时保存截图；报告上传步骤在测试失败后仍执行，测试失败必须使 CI 失败。
6. 遵循仓库已有报告与登录态处理约定。本仓库公开 CI 禁用 trace，不上传认证状态或私有数据；不要为了调试自动开启公开 trace。
7. 实际运行新增测试及与改动相关的现有检查。分别说明代码或配置错误、staging 产品缺陷，以及环境导致的阻塞。
8. 确认测试被 runner 发现，桌面和手机项目均被执行；没有实际运行时不得声称通过。若无法触发远端 CI，明确区分本地验证结果和远端 CI 状态。

## 最终交付

- 已访问的页面、页面类型、样本、视口、语言及未覆盖部分。
- 测试案例表与实际结果。
- 按严重程度排列的问题清单，单独标明缺失或重复 test ID 的问题。
- 可复现步骤和截图证据。
- 新增或修改的 Playwright 测试、配置、运行脚本和 CI 文件。
- 本地与 CI 执行方法，以及真实验证结果。
- 尚未解决的问题和明确的阻塞原因。

直接开始执行。在授权范围内完成可执行的部分；只有确实缺少目标地址、访问条件或关键业务预期时，再向我提出具体问题。
